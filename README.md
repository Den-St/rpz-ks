# Лабораторно-практичне заняття №1 — Програмні моделі систем координат

## 1. Короткий опис роботи

**Мета:** спроектувати та реалізувати імутабельні програмні моделі точок у 2D та 3D системах координат, реалізувати перетворення між декартовою, полярною та сферичною системами, обчислення відстаней різними формулами та провести порівняльний аналіз продуктивності.

**Реалізовані класи** (файл [script.js](script.js)):

| Клас | Поля | Призначення |
|---|---|---|
| `CartesianPoint2D` | `x`, `y` | Точка на площині в декартових координатах. Метод `distanceTo(other)` — евклідова відстань. |
| `PolarPoint` | `radius`, `angle` (рад) | Точка на площині в полярних координатах. Метод `distanceTo(other)` — відстань за теоремою косинусів. |
| `CartesianPoint3D` | `x`, `y`, `z` | Точка у 3D-просторі в декартових координатах. Метод `distanceTo(other)` — евклідова відстань 3D. |
| `SphericalPoint` | `radius`, `azimuth` (φ), `polarAngle` (θ) | Точка у 3D-просторі в сферичних координатах. Методи: `chordDistanceTo(other)` — пряма (хорда), `arcDistanceTo(other)` — дугова (велика колова відстань). |

Імутабельність реалізована через `Object.freeze(this)` у конструкторі — стан об’єкта не змінюється після створення.

Перетворення між системами винесено в **єдину функцію** `convert(point)`, яка за типом аргументу (`instanceof`) визначає напрямок перетворення:

- `CartesianPoint2D` ↔ `PolarPoint`
- `CartesianPoint3D` ↔ `SphericalPoint`

Для кута використовується `Math.atan2(y, x)` (коректна чверть), для полярного кута — `Math.acos(z / r)`. Всі кути — у радіанах.

## 2. Інструкції для запуску проекту

**Вимоги:**
- [Node.js](https://nodejs.org/) версії **12+** (використовується `process.hrtime.bigint()` та числові літерали з `_`).
- Ніяких зовнішніх залежностей, `npm install` не потрібен.

**Запуск:**

```bash
git clone <URL цього репозиторію>
cd pr-1
node script.js
```

Програма послідовно виведе:
1. Результати перевірки коректності перетворень (пряме → зворотне) для 2D та 3D.
2. Перевірку обчислення відстаней на еталонних значеннях.
3. Результати бенчмаркінгу для 2D та 3D (100 000 пар точок, 7 прогонів, медіана).
4. Підсумкову таблицю у Markdown-форматі.

## 4. Результати аналізу продуктивності (Бенчмаркінг)

**Умови вимірювання:**
- Кількість пар точок: **N = 100 000**.
- Кількість прогонів на кожен підхід: **7**, у таблиці — **медіана** (перший прогін часто повільніший через «розігрів» V8).
- Таймер: `process.hrtime.bigint()` — наносекундна роздільність.
- Вимірюється **виключно** цикл обчислень; генерація даних і попередня конвертація Polar→Cartesian/Spherical→Cartesian виконуються поза виміром.
- Середовище: Node.js, macOS.

### Таблиця результатів

| Простір | Підхід | Час, мс (медіана) |
|---|---|---:|
| 2D | Полярні координати (теорема косинусів) | **2.549** |
| 2D | Декартові координати (евклідова) | **2.768** |
| 3D | Сферичні координати, хорда | **6.992** |
| 3D | Сферичні координати, дуга | **8.202** |
| 3D | Декартові координати (евклідова 3D) | **3.675** |

### Аналіз

**2D-простір.** Різниця між підходами мінімальна (~8%). Полярна формула виконує одне множення радіусів, одне віднімання кутів, один `cos` та `sqrt`; декартова — два віднімання, два множення (у `Math.hypot`) і `sqrt`. У JavaScript `Math.hypot` спеціально обробляє переповнення/недоповнення (перевірки та нормалізація), що робить його дещо дорожчим за просту суму квадратів під `sqrt`. Тому в даному тесті поодинокий виклик `Math.cos` виявився не дорожчим за додатковий оверхед `hypot`. Загальний висновок: при малій кількості тригонометричних операцій різниця несуттєва — витрати на них порівнянні з арифметикою в оптимізованому JIT-коді.

**3D-простір.** Різниця тут набагато виразніша:
- **Найшвидший — декартова евклідова (3.675 мс).** Це чисто арифметика: 3 віднімання, 3 квадрати, сума і `sqrt`. Жодного тригонометричного виклику.
- **Сферична хорда (6.992 мс) — приблизно у 1.9× повільніша за декартову.** Формула вимагає **4 тригонометричні виклики** (`sin×2`, `cos×2`) плюс арифметику і `sqrt`. Тригонометрія — це апроксимації рядами / поліномами, вони кратно дорожчі за арифметичні операції.
- **Найповільніший — сферична дуга (8.202 мс).** До тих самих 4 виклики `sin/cos` додається ще й `Math.acos` та клампінг у діапазон `[-1; 1]`. `acos` — теж дорога інверсна тригонометрична функція, тому загальна вартість ще виростає (~2.2× відносно декартової).

Отже, **складність формули напряму корелює з часом виконання**: чим більше тригонометричних викликів — тим повільніше. Різниця не «сотні разів», як подекуди очікують, а помірна — у 2–2.5×, — тому що V8 добре оптимізує гарячі цикли з `Math.*`, але вона стабільно вимірна.

## 5. Загальний висновок

Під час виконання роботи були закріплені навички:

- проектування **імутабельних** моделей даних (`Object.freeze`), як інструменту для безпечного функціонального стилю;
- реалізації **перетворень між системами координат** із коректним використанням `atan2` та `acos`;
- вибору правильної формули відстані під конкретну задачу — хорда (пряма у 3D) vs. дуга (шлях по поверхні сфери);
- проведення **коректного бенчмаркінгу**: використання таймера високої роздільності, «прогрів», багаторазові виміри й медіана замість середнього, ізоляція чистого часу обчислень від підготовки даних.
- **тригонометричні функції — основний драйвер вартості** формул відстаней; там, де формула складніша, а поточне представлення даних не відповідає задачі, часто вигідніше **один раз** сконвертувати дані в декартові координати й далі рахувати простою арифметикою. Це також показує, що вибір моделі даних — це не лише питання зручності API, а й безпосередньо питання продуктивності.
